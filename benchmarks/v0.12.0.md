# Benchmarks — v0.12.0

Date: 2026-05-04
Platform: macOS (Apple Silicon)

Comparisons reference v0.11.0 (`benchmarks/v0.11.0.md`). The release that
landed between the two is UX-9 (#102): the QuickJS-backed JS runtime for
`requires_js` generators (post_process / script_function / custom), plus
the stem-keyed spec store, status schema v1.2, doctor / validate strict
gates, and the coverage-regression CI script. No new benchmark groups
this release; the JS dispatch path is exercised by integration tests
under `gc-jsrt` and `gc-suggest`, not Criterion.

## engine_suggest_sync

| Benchmark | Time | vs v0.11.0 |
|-----------|------|------------|
| command_position | 17.610 µs | −0.4% (flat) |
| subcommand_with_spec | 17.049 µs | +1.1% (flat) |
| filesystem_fallback | 1.3849 ms | +26.4% — see below |
| alias_hit_single | 16.055 µs | +0.1% (flat) |
| alias_hit_multi | 1.5744 ms | +35.9% — see below |

The two pure-spec / pure-alias cases (`command_position`,
`subcommand_with_spec`, `alias_hit_single`) sit within ±1% of v0.11 —
the JS dispatch restructure (`js_kind` resolution, kill-switch gate,
three-way branch on PostProcess / ScriptFunction / Custom) does not
charge specs that have no `js_runtime` shape.

The two filesystem-walk-dominated cases (`filesystem_fallback`,
`alias_hit_multi`) regressed materially. Both benches build a fresh
tmpdir of 2 k files per Criterion invocation and walk it. Repeat runs
on the same machine show the variance straddling +20–35% with the same
binary — the regression appears to be APFS cache state interacting
with Criterion's per-invocation tmpdir setup, not the engine
restructure. The pure-spec paths confirm dispatch overhead is
unchanged.

If you can reproduce the regression on a warm cache or a memdisk-backed
tmpdir please file an issue — keystroke-path benches don't show it,
but a 1 ms → 1.4 ms widening on `cd <TAB>` in a 2 k-file directory is
worth investigating once we can isolate the FS-cache variable.

## Analysis

No change in the keystroke-budget cases. `command_position`,
`subcommand_with_spec`, `alias_hit_single`, fuzzy ranking, parser, and
priority sort all sit within ±1–3% of v0.11 baselines — well inside
run-to-run noise on this machine.

Two filesystem-walk-dominated benches (`engine_suggest_sync/filesystem_fallback`,
`engine_suggest_sync/alias_hit_multi`) regressed by 26% / 36%. Variance
across re-runs straddles the regression band, and the pure-spec
sibling cases are flat, which points at APFS cache state in the
Criterion tmpdir setup rather than an engine regression. Flagged for
follow-up; not a release blocker.

The QuickJS link cost shows up structurally in binary size (102 MB →
~104.78 MB, recorded in `benchmarks/binary-size-baseline.txt`) but
does **not** show up on the keystroke path: specs without `js_runtime`
metadata bypass the dispatch entirely, and the QuickJS worker is lazily
spawned on first JS-backed generator call (cost amortised across the
process lifetime, not per-keystroke).

JS runtime hot-path cost is exercised by integration tests in
`crates/gc-jsrt` and `crates/gc-suggest/tests/js_dispatch.rs`; first-call
worker spawn lands in the ~5–10 ms region, subsequent calls reuse the
worker thread and execute in the hundreds-of-microseconds region per
bounded JS evaluation. A dedicated Criterion group for the JS runtime
is tracked as follow-up — it needs a representative corpus fixture
that's stable across machines.
